# Run workflow products

Follow The Flow does its work through **workflow products** (WPs). Each WP is a whole business operation that runs on the Follow The Flow server: the server decides its steps, checks permissions, and keeps the record. Your job is to pick the WP, gather its input from the person, and decide when the person has to see what will happen before it happens.

## Find the workflow product

1. Call `listWorkflowProducts` to see the WPs the person can use now. It is for discovery only; the server still authorizes every operation. Each WP has an `id` (a UUID) and a `code` such as `wp03`: every tool's `workflowProduct` takes the `code`, never the `id`.
2. Call `getWorkflowProduct` for the one you mean, to learn what it does and what input it needs.
3. Ask the person for any input you do not have. Do not invent values such as amounts, recipients, dates or customers.

A situation may involve more than one WP. For example, "the engagement is done, get it billed and collected" may touch recording the follow-up work, issuing and sending the bill, and writing off the receivable once paid (WP-03, WP-04 and WP-05). Run each WP on its own, with its own prepare and start. Do not describe or reproduce the steps inside a WP, and do not chain the business APIs behind them yourself: the server owns that order.

## Prepare, confirm, start

1. **Prepare.** Call `prepareWorkflowRun` with `{ workflowProduct, input }`. It answers `prepareId`, `preview`, `requiresConfirmation` and `expiresAt`. Preparing changes nothing yet.
2. **Decide whether to ask.**
   - Only when `requiresConfirmation` is exactly `false` may you start without asking (for example WP-03, which only records internal tasks and reminders): skip steps 3 and 4 and go to step 5.
   - When it is `true`, missing, or anything else, you must ask first: do steps 3 and 4 before step 5. WP-04 (issuing and sending bills) and WP-05 (writing off receivables) are `true`: they send something outside the firm or move money.
3. **Show the preview** (only when you must ask). Show the person the whole `preview` the prepare answered, not a summary that drops lines: for WP-04 the bills, recipients and amounts; for WP-05 the matches and differences, as "Write off receivables with WP-05" says. Say in one sentence what starting will do. For WP-04 that is: the run drafts these bills and sends them for approval; nothing is issued or sent until an owner or an admin approves each bill (see "Approve or return WP-04 bills"). Then ask whether to go ahead.
4. **Wait for a clear yes** (only when you must ask). Start only after the person answers yes to this preview. Silence, an unclear answer, or a yes given before they saw this preview is not consent. A yes covers this `prepareId` only.
5. **Start.** Call `startWorkflowRun` with `{ workflowProduct, prepareId }`, the `prepareId` exactly as the prepare answered it. It answers the run; its `id` is the `runId` the other tools take, also exactly as answered.
6. **Follow it.** Use `getWorkflowRun` and tell the person the run's state. A WP-04 or WP-05 run that waits for approval does not go on by itself: say so right away, as "Approve or return WP-04 bills" and "Write off receivables with WP-05" say. A run can wait a long time, for a date or, outside those approvals, for something else: if it is waiting or still running after a few checks, tell them its state, what it waits for when the run says, and its `runId`, and that it goes on by itself. If `getWorkflowRun` fails, say the state is unknown and give the `runId`. When it ends `failed` or `denied`, say so plainly with whatever reason the run gives, and that the steps it finished before stopping are kept: something may already have been sent or recorded, so do not run it again before checking what it did.

If the person changes the input after seeing the preview, prepare again and show the new preview.

### When start does not answer

The run may already have started even when start did not answer with it: the server can replace a successful answer with an error. So whenever start answers with neither a run nor one of the refusals below — it times out, the connection drops, it answers a server error (HTTP 500), or it answers 401 and you have signed in again — call `startWorkflowRun` again with **the same** `prepareId`. A first start answered 403 `insufficient_scope` is not one of these: that start did nothing, so do not retry it; go on as "When the connection lacks a permission" says. The same `prepareId` always answers the same run, so retrying cannot start a second one. Retry up to three times. If signing in again fails, stop retrying and go to the last paragraph of this section.

On such a retry, any refusal — `preview_stale`, `prepare_expired`, `not_found`, `forbidden`, `invalid_input`, `conflict`, `rule_violation`, `idempotency_mismatch` or any other — does not prove that no run started: the first start may still be in progress, or you may now be signed in as someone else. Treat it like no answer, keep the same `prepareId`, and do not follow the refusal table below: it would have you prepare again. The one exception is 403 `insufficient_scope`: retrying cannot get past it, so stop retrying and go on as "When the connection lacks a permission" says for a retry.

If you still have no answer, tell the person in plain words that the run may already have started and that you cannot confirm it yet. When they ask again later, call `startWorkflowRun` with the same `prepareId` first: it answers the run if one exists, even after `expiresAt`. If no run exists and the prepare is still valid, that same call starts it, so make sure they still want it before you call. That later call is still a retry: if it answers a refusal, the run is still unknown, as above. Do not prepare again for a retry: a new prepare followed by a start opens a new run. Prepare again only when the person wants another run on purpose, and after a start whose outcome is unknown, only once they know the first one may exist.

### When start is refused

This table is for a refusal that answers a first start or a prepare. A refusal that answers a retry after a start that did not answer is handled above, and a refusal that answers a cancel is handled under "Cancel a run", not here.

| Refusal                                                               | What to do                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `preview_stale`                                                       | The data behind the preview changed. Answering a first start, it means no run was started: the server answers an existing run for a `prepareId` before it checks expiry or data. (Answering a retry after a start that did not answer, see above.) Prepare again with the same input; never retry the old `prepareId`. If confirmation is required, show the new preview and ask again: the earlier yes was for the old preview. |
| `prepare_expired`                                                     | The prepare is past its `expiresAt` (24 hours after it was made). Same as `preview_stale`.                                                                                                                                                                                                                                                                                                                                       |
| `invalid_input`, `conflict`, `rule_violation`, `idempotency_mismatch` | When the result has `structuredContent`, its `details` list each `field` (a JSON Pointer into the input) and the `reason` (`missing`, `unexpected`, `wrong_type` or `invalid`). Tell the person which field and why, fix the input with them, and prepare again. Without `structuredContent`, tell them the refusal and ask what to change.                                                                                      |
| `forbidden`                                                           | The person may not do this. Tell them; do not look for another way to do it.                                                                                                                                                                                                                                                                                                                                                     |
| `not_found`                                                           | The WP, the `prepareId` or the run does not exist for this person. Tell them.                                                                                                                                                                                                                                                                                                                                                    |

If `prepareWorkflowRun` itself is refused, handle the refusal as this table says. A 403 `insufficient_scope` (on a prepare or a first start) is not in this table and is not `forbidden`: go on as "When the connection lacks a permission" says.

## When the connection lacks a permission

When the person connects Follow The Flow, its consent page always grants reading (`workflow:read`: `listWorkflowProducts`, `getWorkflowProduct`, `getWorkflowRun`, `listApprovalRequests`, `listBankStatements`) and shows a box, ticked, for each other permission your client asked for, which they can clear:

| Box on the consent page                    | Permission        | What it allows                      | Tools that need it                                            |
| ------------------------------------------ | ----------------- | ----------------------------------- | ------------------------------------------------------------- |
| 「準備、啟動與取消工作流程 Run」           | `workflow:write`  | prepare, start and cancel runs      | `prepareWorkflowRun`, `startWorkflowRun`, `cancelWorkflowRun` |
| 「核准或退回核准單（例如開立並寄出帳單）」 | `approval:decide` | approve or return approval requests | `decideApprovalRequest`                                       |

A connection made by entering a code on another device (device sign-in) has no boxes: it gets every permission the client asked for.

A call the connection was not granted is refused before Follow The Flow looks at it, so that call did nothing: HTTP 403 with an `insufficient_scope` challenge whose `error_description` names the permission it needs, for example `workflow:write is required`. (Its `scope` lists every permission, not only the missing one.) If all you see is that the scope was insufficient, the tool you called tells you which permission it was: see the table.

- First check whether the connection was made before these permissions existed: then even reading is refused (a read tool answers this 403, or `error_description` names `workflow:read`; when only a write was refused, one call to `listWorkflowProducts` tells you). Such a connection has to reconnect once, by any way of signing in, device sign-in included; until then every tool but `getUserInfo` is refused this way. Tell the person that; the next bullet does not apply.
- Otherwise, tell the person that this connection was set up without permission to do that, so nothing was done. If they want it done, they reconnect Follow The Flow and keep that box ticked. If the box was not on the page, or they signed in on another device, the client did not ask for that permission: reconnecting the same way will not add it, so tell them that instead. If your client offers to sign in again with more permissions, that sign-in does ask for it. Do not look for another way to do it, and do not say Follow The Flow refused them: the connection did.
- Your client may offer to sign in again with more permissions. Whether to reconnect is the person's choice: tell them what the box allows and let them decide.
- After they reconnect, a run that was refused at prepare or at a first start starts over: prepare again and go on as "Prepare, confirm, start" says, deciding by what the new prepare answers. When its `requiresConfirmation` is exactly `false`, start without asking; otherwise show the new preview and get their yes again: a yes given before reconnecting does not carry over to the new prepare. A first decide (approve or return) refused this way did nothing, and that yes does not carry over either: once they have reconnected, list without a `status`, following `nextCursor`, until you find its `id`: if it no longer shows `pending`, tell them what it shows and send nothing; if you do not find it or a page fails, say its state is unknown and send nothing; if it still shows `pending`, show it with the fields of its kind (a bill, or a WP-05 difference as "Write off receivables with WP-05" step 4 says) and the reason for a return, ask them again, and send it with the `version` that listing answered.
- A first cancel refused this way did nothing, so the run goes on as before: tell the person that. Once they have reconnected, make sure they still want it cancelled, then go on as "Cancel a run" says, with the same `workflowProduct` and `runId`.
- On a retry after a start, cancel or decide that did not answer, this 403 says only that the retry did nothing; the first call may still have gone through, so the "starts over" bullet above does not apply, and do not say nothing was done. Tell the person that. Once they have reconnected, a start goes on as "When start does not answer" says: make sure they still want it, since that call starts the run if none exists yet, then call `startWorkflowRun` again with the same `prepareId`, which answers the run if one exists, and do not prepare again. For a cancel, first find out what happened, as "Cancel a run" says under "Find out what happened" (reading still works): if the run shows `cancelled` or finished, or `getWorkflowRun` fails, tell them what that paragraph says and stop. Only if it is still running or waiting, once they have reconnected, make sure they still want it cancelled, then go on as "Cancel a run" says, with the same `workflowProduct` and `runId`. For a decide, look the request up first as "Approve or return WP-04 bills" step 4 says (reading still works), and never send the opposite decision while its outcome is unknown. Once they have reconnected, list it again: if it no longer shows `pending`, tell them what it shows and send nothing; if it still does, show it with the fields of its kind (and the reason, for a return) and ask them again before you send it, with a new `commandId` only if the decision, reason or version changed.
- Any other refusal or a 401 is not this: handle it as the other sections say ("Cancel a run" for a cancel). A `forbidden` refusal is Follow The Flow refusing the person, and reconnecting does not change it.

Examples:

- `prepareWorkflowRun` answers 403 `insufficient_scope`. You call `listWorkflowProducts`, and it answers. You say: "This Follow The Flow connection was set up without permission to prepare and start runs, so nothing was prepared. To do it, reconnect Follow The Flow and keep 「準備、啟動與取消工作流程 Run」 ticked." You do not retry.
- `prepareWorkflowRun` answers 403 `insufficient_scope`, and `listWorkflowProducts` does too. You say: "This Follow The Flow connection was made before its current permissions existed, so it cannot do anything yet. Reconnect Follow The Flow once, any way you like, and reading works again; preparing runs also needs 「準備、啟動與取消工作流程 Run」 kept ticked." You do not retry.
- After reconnecting, the person asks again. You prepare again; the prepare answers `requiresConfirmation: true`, so you show the new preview and ask for their yes. Had it answered `false` (as WP-03 does), you would start without asking.
- `cancelWorkflowRun` answers 403 `insufficient_scope` on the first call. You say: "This connection was set up without permission to cancel runs, so the run was not cancelled and goes on. To cancel it, reconnect Follow The Flow and keep 「準備、啟動與取消工作流程 Run」 ticked." After they reconnect, you ask whether they still want that run cancelled; on their yes you call `cancelWorkflowRun` with the same `workflowProduct` and `runId`.

## Approve or return WP-04 bills

A WP-04 run, started by a person or by the schedule, drafts the bills and sends each one for approval, then waits (`getWorkflowRun` shows it `waiting`). Tell the person: the bill drafts were sent for approval, a bill is issued and its sending requested only after an owner or an admin approves it, and a bill nobody decides within 7 days is returned. Never approve or return a bill on your own: a yes to the run's preview is not a yes to its bills.

The same list holds both kinds of request, told apart by `subjectKind`: `invoice_proposal` is a WP-04 bill, handled in this section; `bank_transaction` is a WP-05 payment difference, shown and decided as "Write off receivables with WP-05" step 4 says. Show each request with the fields of its own kind, never a payment difference as a bill, and never let one yes cover both kinds.

When the person wants to approve or return bills:

1. **List.** Call `listApprovalRequests` with `{ status: "pending" }`. Show every WP-04 bill (`subjectKind` `invoice_proposal`) it answers, one by one, with what its `summary` gives: the customer, who the bill is addressed to (`billTo`), the amount and the currency. A pending bill has no due date yet: tell the person its payment due date is set when it is approved, 30 days after the approval date (Taipei); do not show any other date as its due date. When it answers a `nextCursor`, call it again with the same `status` and that `cursor` for the rest before you ask; if there are more than you can show, say how many and ask which to look at first. If the first page is refused (`forbidden`, for example, when this person may not read the firm's approvals), tell the person and decide nothing; a 403 `insufficient_scope` here means the connection was made before these permissions existed, as "When the connection lacks a permission" says.
   - **Bills that look the same.** One customer can have several bills with the same bill-to, amount and currency. When two shown bills match on all four, also show when each was requested (`requestedAt`) and the last characters of its `id`, so the person can tell which is which. If they still cannot tell them apart, ask before you decide either; do not pick one for them. The same holds when the person names a bill ("approve Acme's") and more than one shown bill matches: ask which, and do not decide them all.
   - **A page that fails.** If any page of the list does not answer or is refused, the list you have is incomplete: tell the person so, show what you have as incomplete, and do not ask them to approve or return "all". You may still decide a bill they pick by name from what you showed, with their yes to that one.
2. **Get a yes for each one.** Call `decideApprovalRequest` only for a request the person has explicitly approved or returned after seeing that bill. When they say "approve all" or the like, and every page of the list answered, list all of them again with customer, bill-to, amount and currency and ask once more whether every one of them is approved; only a yes to that list covers them, one call per request.
3. **Returning needs a reason, and a yes.** Ask the person why, unless they already said why, and send their reason as `reason` (at most 500 characters; shorten it with them if it is longer). Do not return a bill without one, and do not make one up. A reason is not a yes: before you send, show the bill and the reason again and ask whether to return this one with it.
4. **Decide.** Call `decideApprovalRequest` with `{ approvalRequestId, expectedVersion, decision, reason?, commandId }`: the request's `id` and `version` exactly as the list answered them, `decision` `approved` or `returned`, and a `commandId` you make as a new UUID the first time you send this decision. When the call does not answer (a timeout, a dropped connection, a server error, or 401 and you have signed in again), send the same decision again with the same `commandId`: the same `commandId` answers the same decision and never decides twice. Resend up to three times. On a resend, a refusal (such as `conflict`) does not prove the decision was not made: your first send may already have decided it, so treat it like no answer. The one exception is 403 `insufficient_scope`: resending cannot get past it, so stop resending and go on as "When the connection lacks a permission" says for a retry. If none of them answers, or signing in again fails, stop resending: list the requests without a `status`, following `nextCursor` page by page until you find this `approvalRequestId`, and tell the person what it shows. If it still shows `pending`, your first send may still be on its way: tell the person so, and list again before you send any other decision for it. If you do not find it, or a page of that listing fails, its outcome is unknown: tell the person the decision may already have taken effect and you cannot confirm it yet, and list again before deciding anything when they ask later. While the outcome is unknown, never send the opposite decision (returning a bill you may have approved, or the reverse): the first one may already have taken effect. Any change to the decision, the reason or the `expectedVersion` takes a new `commandId`.
5. **Tell the person what happened**, by what the call answered. This step is for a first send; a refusal on a resend is step 4's case, since your first send may have decided it:
   - **The request, approved or returned.** Say that this bill was approved, or returned; do not say it was issued or sent, because deciding it does neither. When every request of the run has an answer, the run goes on by itself: it issues the approved bills and requests their sending, and does not issue the returned ones. Follow the run with `getWorkflowRun`, its `runId` being the request's `workflowRunId` and its `workflowProduct` `wp04`, and report issuing and sending only when the run reports them; a request without a `workflowRunId` has no run to follow.
   - **403 `insufficient_scope`.** The connection was not granted 「核准或退回核准單」, so this call did nothing; it is not `forbidden`. Go on as "When the connection lacks a permission" says. (A 403 on a resend is step 4's case: your first send may have decided it.)
   - **`forbidden`.** This person may not decide it: only an owner or an admin of a firm with WP-04 may approve or return bills. Tell the person that, and do not retry or look for another way. (A `forbidden` on a resend is step 4's case: your first send may have decided it.)
   - **`conflict`.** The request is no longer pending, or it changed since you listed it: someone else may have decided it. List again without a `status`, following `nextCursor` page by page until you find that request, so it shows whatever state it is in now, and show what changed. If it is still pending, decide again only with the person's new yes, using its new `version` and a new `commandId`. If you do not find it, or a page of that listing fails, tell them its state is unknown. (A `conflict` on a resend is step 4's case: your first send may have decided it.)
   - **`not_found`.** The request does not exist for this person. Tell them and list again.
   - **`invalid_input`, `rule_violation`** (or another refusal with `details`). Say which field and why, as the `details` give them, fix it with the person, and decide again with a new `commandId`. A return without a reason answers `invalid_input` on `/reason`.
   - **`idempotency_mismatch`.** That `commandId` was already sent with other input. Make a new one only after the person confirms the decision as it is now.
   - **An `Input validation error`** (the call did not reach Follow The Flow, for example a reason over 500 characters). Fix the input with the person and decide again.

A request that nobody decides within 7 days expires: the bill is returned with the reason that approval timed out, and the run finishes without it.

Say a bill was delivered only when the run says so. For now no mail provider is connected for bills: the run's result records each sending as requested, so say the bill was issued and its sending requested, not that the customer received it.

### Examples

- The person: "Bill this month's installments." You prepare WP-04, show the bills, get a yes, start it; `getWorkflowRun` shows `waiting`. You say: "The bill drafts were sent for approval. A bill is issued and its sending requested only after an owner or an admin approves it. A bill nobody decides within 7 days is returned." You do not call `decideApprovalRequest`.
- The person: "Approve the bills." You call `listApprovalRequests` with `{ status: "pending" }` and show each: customer, bill-to, amount and currency, and say each due date is set at approval, 30 days after the approval date (Taipei). They answer "approve the first two". You call `decideApprovalRequest` twice, once for each of those two, each with its own new `commandId`, and leave the rest pending. You say the two were approved; you say they were issued only when `getWorkflowRun` reports it.
- The person: "Approve all of them." You list all pending bills again with customer, bill-to, amount and currency and ask: "Approve all three of these?" Only after their yes do you decide each one.
- The person: "Return the one for Acme." You list the pending bills and show Acme's; if Acme has more than one, you ask which. You ask why. They say "the amount is wrong". You show Acme's bill again and ask: "Return this one with the reason 'the amount is wrong'?" Only after their yes do you return it with `reason` "the amount is wrong". Without their reason, or without that yes, you do not call.
- The call answers `forbidden`. You say: "You can't approve this bill: only an owner or an admin of a firm with WP-04 can." You do not retry.
- The call answers `conflict`. You say the bill may have been decided by someone else, list again without a `status`, following `nextCursor` until you find it, and show what it says now; if it is still pending, you ask again before deciding.
- The first call times out. You call again with the same `approvalRequestId`, `expectedVersion`, `decision` and the same `commandId`. If three resends do not answer either, you stop, list without a `status` until you find it, and say what it shows, or that the decision is not confirmed yet; you do not send the opposite decision meanwhile.

## Write off receivables with WP-05

WP-05 reads one bank statement and writes off the customers' open invoices against the payments in it. It works only on a statement a person has already uploaded on the Follow The Flow web app: you cannot upload one, and there is no tool for it. If the person says it is not uploaded yet, still do step 1's check that the firm has WP-05 before asking anyone to upload it.

When the person asks to decide WP-05 differences that are already waiting ("approve the pending bank differences"), with no run started in this conversation, go straight to step 4 "When the person wants to decide them": its list, yes and follow-up rules apply, by run as step 4 says.

1. **Find the statement.** Call `listBankStatements`, with `treasuryAccountId` or `periodEndFrom` / `periodEndTo` when the person names the account or the period, following `nextCursor` for more. If a later page does not answer or is refused, the list is incomplete: say so, show what you have as incomplete, and do not conclude that a statement is the only one, the latest or the one they mean; prepare only one the person picks from what you showed. Show the statements it answers, each with its period (`periodStart` to `periodEnd`), when it was uploaded (`importedAt`), how many transactions it has (`transactionCount`) and how many of them are already received (`receivedCount`), and with its treasury account (`treasuryAccountId`) when they differ, so that statements of different accounts, or the same period uploaded twice, are told apart (ask the person which account they mean when the ids do not tell them), and agree with the person which one to process; if more than one fits what they said, ask which. Do not guess. The list is open only to a firm with WP-05. `listWorkflowProducts` lists the WPs this person can use, not every WP the firm has: when `wp05` is not there, WP-05 is not available to this person, either because the firm has not enabled it or because they do not have access to it; never say which. When it answers `forbidden`, call `listWorkflowProducts`: if `wp05` is there, this person may not read the firm's bank statements, so tell them to ask an owner or admin; if it is not, say WP-05 is not available to them and that an owner or admin can tell them why. Either way, stop. When it answers no statement, check with `listWorkflowProducts` that `wp05` is there before asking for an upload: if it is, ask the person to upload the statement on the web app, or to ask someone in the firm who can; if it is not, say WP-05 is not available to them (an owner or admin can tell them why) and stop. If `listWorkflowProducts` does not answer or is refused (other than with a 403 `insufficient_scope`), do not ask for an upload: after an empty list, say you cannot confirm WP-05 is available to them; after `forbidden`, say WP-05 may not be available to them or they may not read the firm's bank statements. A 403 `insufficient_scope`, from `listBankStatements` or from that `listWorkflowProducts` check, is not `forbidden` and says nothing about WP-05: go on as "When the connection lacks a permission" says, and do not say the firm lacks WP-05; once they have reconnected, list the statements again.
2. **Prepare.** Call `prepareWorkflowRun` with `{ workflowProduct: "wp05", input: { bankStatementId } }`, the statement's `id` exactly as the list answered it. WP-05 always requires confirmation: do steps 3 and 4 of "Prepare, confirm, start" as below before any start.
3. **Show the matches and differences.** For WP-05 the whole preview is what follows: the lines handled by themselves are shown as totals, and you show any of them line by line when the person asks. From the `preview`, show:
   - The `totals`: how many transactions, how many lines will be handled by themselves (`auto`) and how much came in on them, how many will wait for approval (`approval`) and how much came in on them, how many become a task for a person (`workItem`; such a line's `handling` is spelled `work_item`, and the result's count `workItems`), and how many are left alone (`none`). Each amount is what the bank paid in on those lines (`received`), not what will be applied to invoices: an `auto` line may also be a payment with no open invoice or an overpayment, which leaves money unapplied, so never call a total the amount written off.
   - Every line whose `handling` is `approval` or `work_item`, one by one: the customer (`customerName`, or say the payer is unknown), what was received (`received`), what its invoices have open (`expectedOpen`), the difference between the two, the invoices and amounts it would be applied to (`allocations`), and why it was classified so (`reason`). When a line has no open invoice or no allocation, say so instead of a difference. The line's kind is its `category`: for a `fee_difference` say the firm would absorb the bank fee (`fee`) so the invoices are settled in full; for an `underpaid` say the customer paid less and the invoices would stay partly open.
   - When `truncated` is true, say the preview shows only part of the lines, and that the totals count them all.

   In everything WP-05 shows, the preview and the approvals alike, show the counterparty only as `counterpartyMasked`; never ask for or repeat a full account number. If the person asks for it, say you only see the masked number. Then say what starting will do: the run applies the `auto` lines, sends each `approval` line for approval, and opens a task for each `work_item` line; nothing waiting for approval is applied until an owner or an admin approves it. Ask whether to go ahead, and start only on a clear yes to this preview.

4. **Approve each difference.** After the start, check the run with `getWorkflowRun`. Only when it shows `waiting` does it wait for approvals, and then it does not go on by itself; when it has ended, skip to step 5 (a run can end without waiting, for example when its data changed after the start, or when the preview's `totals` counted no `approval` line). Go by the run's state, not by the lines shown (a `truncated` preview may show no `approval` line while some wait); the `totals` tell you how many to expect. While it waits, tell the person right away that these differences wait for an owner or an admin, and that a difference nobody decides within 7 days expires and is left for a person to handle. Never approve on your own: a yes to the preview is not a yes to a difference. When the person wants to decide them:
   - **List.** Call `listApprovalRequests` with `{ status: "pending" }`, following `nextCursor`, as "Approve or return WP-04 bills" step 1 says (a page that fails makes the list incomplete). The list holds every pending request of the firm, of other runs too: a request belongs to this run only when its `workflowRunId` is this run's `runId`. Show this run's differences, and show any other `bank_transaction` request apart, grouped by its `workflowRunId` (or as having none), never mixed into this run's. With no run of this conversation (the entry above), group them all by `workflowRunId` and ask which run's differences the person means. For each `bank_transaction` request you show, show: the customer (`summary.customerName`), when it came in (`summary.bookingDate`), what was received (`proposal.received`), what its invoices had open (`proposal.expectedOpen`), the difference between the two, each invoice and amount it would be applied to (`proposal.allocations`), and who bears the difference, from `proposal.category`: `fee_difference` means the firm absorbs the bank fee (`proposal.fee`) and the invoices are settled in full; `underpaid` means the customer paid less and the invoices stay partly open. When two shown differences match on customer, `proposal.received`, `proposal.expectedOpen` and `summary.bookingDate`, also show when each was requested (`requestedAt`) and the last characters of its `id`, and ask which if the person still cannot tell them apart.
   - **Get a yes for each one.** Call `decideApprovalRequest` only for a request the person explicitly approved or returned after seeing that difference. When they say "approve all" or the like, and every page answered, it means one run's differences: list every difference of that run again with the fields above and ask once more; only a yes to that list covers them, one call per request, and never a request of another run.
   - **Return and decide.** A return needs the person's reason and a yes to it, and each decision is sent with its own new `commandId`, resent unchanged when a call does not answer, exactly as steps 3 and 4 of "Approve or return WP-04 bills" say.
   - **What the call answered.** Approved or returned: say that this difference was approved or returned; do not say it was written off. When every request of the run has an answer, the run goes on by itself: it writes off the approved differences and leaves each returned one for a person as a task. Follow it with `getWorkflowRun`, its `runId` being the request's `workflowRunId` and its `workflowProduct` `wp05`, and report write-offs only when the run reports them; a request without a `workflowRunId` has no run to follow. On `forbidden` to a first decide: only an owner or an admin of a firm with WP-05 may approve or return a difference; tell the person and do not retry. A `forbidden` to a resend is step 4 of "Approve or return WP-04 bills"'s case: your first send may have decided it. A 403 `insufficient_scope` is not `forbidden`: on a first decide, handle it as step 5 of "Approve or return WP-04 bills" says (the call did nothing); on a resend, as its step 4 says. Any other refusal is handled as step 5 of "Approve or return WP-04 bills" says.

5. **Report the result.** When the run ends `completed` with `result.stale` true, it wrote nothing: the data behind the preview changed after the start. Say so plainly, and offer to prepare again, which shows a new preview that needs a new yes. Otherwise say what its `result` says it did: what was received (`received`), how many approvals were approved, returned or expired (`approvals`), how many tasks it opened (`workItems`), how many transactions it did not handle (`notHandled`) and how many it could not process and left to a person as a task (`skipped`). A completed run has written off what it could; it does not mean the bank reconciliation is finished, so do not say the statement is reconciled. When `result.deferred` is more than 0, the run handled only part of the statement: tell the person how many transactions are left and that running WP-05 again on the same statement handles them.

### WP-05 examples

- The person: "Write off this month's payments." You call `listBankStatements`; nothing for this month is there, and `listWorkflowProducts` lists `wp05`. You say: "I can't find this month's statement. Please upload it on the Follow The Flow web app first, or ask someone in your firm who can; I can't upload it for you." You do not prepare.
- The person: "Process the November statement." `listBankStatements` answers no statement and `listWorkflowProducts` has no `wp05`. You say: "WP-05, the bank write-off, isn't available to you: either your firm hasn't enabled it or you don't have access to it. An owner or admin of your firm can tell you which." You do not ask them to upload.
- The person: "Process the November statement." `listBankStatements` answers one for November; you prepare WP-05 with its `id`, show the totals and each `approval` and `work_item` line (customer, received, open, difference, invoices, reason), and ask: "Go ahead?" Only after their yes do you start.
- A WP-05 request is `fee_difference`, received 9,985, open 10,000, fee 15. You say: "Acme paid 9,985 against invoice INV-0007 with 10,000 open. Approving it settles the invoice in full and the firm absorbs the 15 bank fee. Approve?" Only after their yes do you decide it.
- The decide answers `forbidden`. You say: "You can't approve this difference: only an owner or an admin of a firm with WP-05 can." You do not retry.
- The run ends `completed` with `deferred` 50. You say what it did, that 50 transactions are left, and that running WP-05 again on the same statement handles them; you do not say the statement is reconciled.

## Cancel a run

Call `cancelWorkflowRun` with `{ workflowProduct, runId }`. Then act on what it answers:

- **The run, with status `cancelled`.** Tell the person the run is cancelled. Cancelling a run that is already cancelled answers the same result again.
- **`cancel_not_allowed`.** The cancel did not happen, and that is final. A run can be cancelled only before any step that sends something outside the firm or moves money has begun; after that the answer is `cancel_not_allowed`. The same answer comes for a run that has already finished (`completed`, `failed` or `denied`). Tell the person it is too late to cancel: what was actually sent or paid stays, and undoing it is a separate business action they start themselves, such as voiding the invoice or undoing the reconciliation match. Nothing rolls back on its own. Check the run with `getWorkflowRun` to tell them where it stands; if that fails, say its state is unknown and give the `runId`.
- **No answer** (a timeout, a dropped connection, a server error, or 401 and you have signed in again). Call `cancelWorkflowRun` again with the same `runId`: cancelling twice answers the same. If it still does not answer, find out what happened (below).
- **401, and signing in again fails.** Tell the person that signing in failed, so the cancel may not have gone through and cannot be confirmed, and that they need to sign in before the run can be checked or cancelled. Give the `runId`.
- **403 `insufficient_scope`.** The connection was not granted the permission to cancel: go on as "When the connection lacks a permission" says, not as the next bullet.
- **Another refusal** (`forbidden`, `not_found` or any other). Tell the person the refusal, then find out what happened (below). Never prepare from a cancel: preparing is the first step of a new run, the opposite of what they asked.

**Find out what happened.** Call `getWorkflowRun`. If it shows the run `cancelled`, tell the person it is cancelled. If it shows the run finished (`completed`, `failed` or `denied`), the cancel did not happen: tell them as for `cancel_not_allowed` above. If it shows the run still running or waiting, tell them that state and that the cancel is not confirmed; they can ask to cancel again. If `getWorkflowRun` fails or is refused, say the cancel is not confirmed and the state is unknown, and give the `runId`. Say a run is cancelled only when `cancelWorkflowRun` or `getWorkflowRun` shows it `cancelled`.

## Why you still ask when the server checks

Asking the person is how they stay in control of what is sent and paid in their name. It is not a security check: the server authorizes every start again, refuses a prepare that has expired or whose data changed, and does not know whether you asked. That is not a reason to skip asking; it is the reason asking is your job.
